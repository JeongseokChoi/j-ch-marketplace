# Workflowy 작업 흐름 기록

인자는 훅이 먼저 처리하고 결과를 `[workflowy]` 로 알려준다. 명령을 따로 실행하지 않는다.

| 인자 | 훅이 한 일 | 할 일 |
|---|---|---|
| 노드 id·URL | 이 세션을 그 노드에 기록하도록 등록. 요청 목록은 Workflowy 에서, 요청의 하위는 이 PC 에 남은 기록에서 이어받는다 | "기록 시작" 이면 아래 지침대로 **이 세션이 끝날 때까지** 기록한다. 실패면 이유를 사용자에게 전한다 |
| `sync` | Workflowy 에서 root 아래 전체를 다시 읽는 백그라운드 프로세스를 띄우고 곧바로 끝난다 | 결과가 올 때까지 지금 기록으로 일한다. 결과는 다음 사용자 메시지나 workflowy 도구 결과 뒤에 `[workflowy] sync 끝남` 으로 온다 (앞 sync 의 결과를 아직 전하지 않았으면 이 응답에 먼저 붙는다). 그 트리로 흐름을 다시 파악하고, 끝나지 않은 todo 가 있으면 사용자에게 묻는다 (아래 **이어받기**) |
| `stop` | 기록 중단 | 이후 workflowy 도구를 쓰지 않는다 |
| `doctor`, 없음 | 점검·현재 상태 | 결과를 사용자에게 그대로 전한다 |

id 뒤에 적힌 나머지 글은 사용자의 첫 요청이다.

## 목적

사용자는 이 기록으로 Claude 의 작업을 **지금 지켜보고**, **남겨 두고**, **나중에 파악**한다.
대화를 보지 않고 이 노드만 읽어도 무엇을 왜 어떻게 했고 결과가 어땠는지 알 수 있게 쓴다.
일이 진행되는 대로 바로 쓴다. 끝나고 몰아서 쓰면 지켜볼 수 없다.

root 노드는 **작업 흐름 하나**다. 세션이 바뀌어도 사용자는 같은 root 로 시작하고, 기록은 그 아래에 이어진다.

## 쓰는 방법

`workflowy` MCP 서버의 두 도구만 쓴다.

- `create(parent, name, type, note?, steps?, request?)` — parent 의 맨 아래에 노드를 추가하고 id 를 돌려준다.
  parent 는 root 이거나, 이 세션에서 만들었거나 이어받은 노드. 돌려받은 id 로 하위 노드를 이어 붙인다.
  **root 바로 아래에는 요청만 쓴다**: 새 요청은 `create(parent=root, name, request: true)`.
  **방금 만든 노드 아래에 쓸 노드는 그 id 를 받은 뒤에 부른다** (같은 메시지에서 함께 부르지 않는다).
- `close(ids, outcome, reason?)` — 이 세션에서 만들었거나 이어받은 todo 를 닫는다. 끝냈는지, 취소·방향 전환·보류인지를
  outcome 으로 고른다 (아래 **todo 닫기**).

**root 노드 자체와 이미 쓴 노드는 고치거나 지우지 않는다.** 그런 도구도 없다.
잘못 쓴 내용은 바로잡는 노드를 새로 추가한다. 호출이 거부되면 이유를 읽고 고쳐서 다시 부른다.

| type | 쓰임 |
|---|---|
| `bullets` | 발견, 결정, 막힌 점 같은 짧은 항목 (기본값). 요청 안의 큰 주제도 bullets 로 두고 하위를 들여 쓴다 (요청 자체는 `request: true`) |
| `todo` | 순서대로 해 나갈 작업 (Phase, 단계, 하위 작업) |
| `p` | 계획·결과처럼 문장으로 풀어 쓰는 단락 |
| `quote-block` | 사용자 요청 원문, 인용할 출력 |
| `code` | 핵심 명령, 오류 메시지, 짧은 코드 조각. name 에 원문을 그대로 (여러 줄 가능) |

제목 서식(h1·h2·h3)은 쓰지 않는다. 구획은 bullets 와 들여쓰기로 나눈다.

name 은 한 줄 평문 제목이다. 서식은 붙지 않는다 (요청 제목의 굵게만 서버가 붙인다). 서식을 넣으려 하지 않는다.
Workflowy 가 서식이나 태그로 읽는 글자는 서버가 비슷한 글자로 바꿔 보낸다: `<` `>` → `‹` `›`, `*` → `∗`, 백틱 → `ˋ`.
긴 설명은 note 에 넣는다. 사용자와 대화하는 언어로 쓴다.

## 구조 (권장)

root 바로 아래에는 요청만 들어간다. 요청 아래는 자유롭게 구성해도 된다. 따로 정한 게 없으면 이렇게 한다.
**세션마다 구획을 따로 만들지 않는다.** 요청마다 root 바로 아래에 `request: true` 로 요청 노드를 만든다.

```
<root>                                        ← 작업 흐름. 건드리지 않는다
├─ **인증 미들웨어 3단계 분리**               request: true 로 만든 요청. note: 2026-09-23 14:05 (자동)
│  ├─ quote-block  요청 원문 (길면 요지)
│  ├─ p  계획: verify/extract/inject 로 나누고 호출부를 옮긴다
│  ├─ ☑ todo  Phase 1 · 구조 파악
│  │  ├─ ▹ 미들웨어 파일 탐색                 ← 훅이 자동으로 붙인다
│  │  └─ bullets  발견: 검증·추출·주입이 한 함수에 섞여 있음
│  ├─ ☐ todo  Phase 2 · 분리 구현
│  │  ├─ ▹ auth.py 분리
│  │  └─ bullets  결정: jwt v9 시그니처에 맞춰 verify() 를 감싼다 — 호출부 3곳이 v8 방식
│  └─ p  결론: 테스트 12건 통과. 남은 일: 배포 설정 확인
└─ **다음 요청 …**                            다른 세션의 요청도 같은 식으로 이어진다
```

요청 노드의 note 첫 줄에는 서버가 날짜·시각을 붙인다. 세션의 경계는 이것으로 알아본다.
날짜를 직접 쓰지 않는다 (note 를 주면 그 다음 줄에 이어진다). 제목의 굵게도 서버가 붙인다.
기록을 시작할 때 이 세션에서 이미 진행한 작업이 있으면, 그 내용을 먼저 짧게 정리해 둔다.

## 이어받기

root 아래에 이미 노드가 있으면, 기록을 시작할 때 훅이 이어받았다고 알리고
지금까지의 트리(길면 요청 목록, 열린 todo, 보류된 todo, 마지막 요청)를 id 와 함께 보여준다.
시작을 빠르게 하려고 **요청 목록만 Workflowy 에서 읽고, 요청의 하위는 이 PC 에 남은 기록**을 쓴다.
다른 PC 의 기록이나 사용자가 Workflowy 에서 직접 적거나 고친 내용까지 봐야 하면 사용자에게
`/workflowy:workstream sync` 를 권한다 (Claude 가 직접 부를 수는 없다). sync 는 root 아래 전체를 백그라운드에서
읽고, 끝나면 결과를 다음 사용자 메시지나 workflowy 도구 결과 뒤에 한 번 전한다. sync 결과가 필요한 일은 결과가 온 뒤에 한다.
todo 앞의 표시는 ☐ 열림, ⏸ 보류, ✓ 완료, ✕ 취소, ↪ 변경이다. 요청 옆에는 만든 날짜·시각이 붙는다.

- 먼저 그 내용으로 이전 흐름을 파악하고 지금 요청과 이어지는지 본다. 보이는 건 제목뿐이다 (note 는 없다).
- 이전 요청을 이어서 하는 일이면 그 요청 아래에 덧붙여도 된다. 새 요청이면 root 아래에 `request: true` 로 새 요청 노드를 만든다.
- **끝나지 않은 todo(☐ 열림, ⏸ 보류)가 있으면 혼자 판단해 닫거나 이어서 하지 않는다.** 사용자가 적어 둔 할 일일 수도 있다.
  목록을 보여 주고 각각 어떻게 할지 사용자에게 묻는다: 이어서 하기 / 끝난 것으로 닫기(`done`) / 취소(`cancel`) /
  보류(`hold`) / 그대로 두기. 사용자가 이미 지시했으면 묻지 않고 따른다.
- 보류된 todo 를 같은 방법으로 이어서 하기로 하면 그 아래에 재개 todo 를 만들고, 방법이 바뀌었으면 `replace` 로 닫고
  새 요청을 만든다 (아래 **todo 닫기**).
- 이어받은 노드에는 도구 실행이 자동으로 붙지 않는다. 이어받은 todo 를 이어서 진행하려면 그 아래에 새 todo 를 만든다.
- 다 읽지 못하면 훅이 알린다. sync 에서 호출이 실패한 노드는 `[하위 일부: 이 PC 기록]` 으로 표시되고 제목이 나열되며,
  읽기에 실패하면 이 PC 에 남은 기록으로 이어받는다 (sync 는 상태를 그대로 둔다). 그 부분은 Workflowy 와 다를 수 있다.

## todo 와 진행 단계

도구 실행(Bash 등의 description, 편집한 파일 이름)은 훅이 **지금 작업 중인 노드** 아래에 `▹` 로 자동으로 붙인다.
지금 작업 중인 노드는 이렇게 정해진다: 트리 순서로 **닫히지 않은 첫 todo** 를 찾아 그 안의 열린 todo 로 끝까지
내려간 것 (보류된 todo 는 건너뛰고 그 아래만 본다). 열린 todo 가 없으면 이 세션에서 마지막으로 만든 요청이나 `steps: true` 로 만든 노드. 그래서:

- 여러 단계로 할 일은 **착수 전에 todo 를 순서대로 모두 만들고**, 하나 끝날 때마다 **바로 close** 한다.
  close 를 늦게 하면 다음 단계의 도구 실행이 앞 단계 아래에 쌓인다.
- 단계에서 나온 발견·결정·결과는 **그 todo 아래에 쓰고 나서** close 한다. 모든 단계를 끝낸 뒤 몰아서 쓰지 않는다.
  따로 쓸 게 없던 단계는 reason 에 한 줄 결과를 넣는다. 요청 전체의 결론만 마지막에 요청 노드 아래에 쓴다.
- 단계 안의 하위 작업도 todo 로 만들 수 있다. Phase 가 아니어도 체크해 나갈 일이면 todo 로 만든다.
- 지금 하는 작업이 아닌 todo (후속 과제, 사용자에게 남긴 일) 는 `steps: false` 로 만든다.
- 하지 않게 된 todo, 미룬 todo 는 열어 두지 않고 **todo 닫기** 대로 닫는다. 열어 두면 이후 도구 실행이 계속 거기 붙는다.
- 한 번에 끝나는 간단한 요청은 todo 없이 요청과 결과만으로 충분하다.

도구의 description 은 그대로 기록되므로, **사용자와 대화하는 언어로** 지금 하는 일을 명사형으로 짧게 쓴다
(예: `설치본과 저장소 코드 비교`). 기록 중에는 사용자 요청마다 훅이 이 지침을 한 줄로 상기시킨다.

## todo 닫기

todo 는 `close(ids, outcome, reason?)` 로 닫는다. 되돌리거나 다시 열 수 없다. **하지 않은 todo 를 done 으로 닫지 않는다.**

| outcome | 언제 | Workflowy 에 남는 것 | reason |
|---|---|---|---|
| `done` (기본) | 끝냈다 | 체크 (reason 은 `결과: …`) | 그 todo 아래에 쓴 결과가 없으면 필수 |
| `cancel` | 하지 않기로 했다 | `✕ 취소: …` + 체크 | 필수 |
| `replace` | 계획이 바뀌어 다른 방법으로 대신한다 | `↪ 변경: …` + 체크 | 필수 |
| `hold` | 나중에 이어서 한다 (사용자가 미룸, 외부 조건 대기) | `⏸ 보류: …`, 체크하지 않음 | 필수 |

- `ids` 에 여러 todo 를 주면 같은 outcome·reason 으로 각각 닫는다. 이유는 todo 마다 쓰인다.
  아직 닫지 않은 하위 todo 가 있으면 거부되므로 ids 에 함께 넣는다.
- **계획이 바뀌면** 남은 todo 를 한꺼번에 `replace` 로 닫고, 바뀐 계획(p)과 새 todo 를 요청 아래에 쓴다.
  옛 todo 를 열어 둔 채 새 todo 를 만들면 새 todo 는 맨 아래에 붙으므로, 도구 실행이 앞에 있는 옛 todo 에 붙는다.
- 보류된 todo 에는 도구 실행이 붙지 않는다. **같은 방법으로 이어서 하면 그 아래에 재개 todo 를 만든다.**
  재개 todo 가 지금 작업 중인 노드가 되고, 이전 기록과 이번 기록의 경계가 된다 (note 에 날짜·시각).
  재개 todo 를 모두 끝내면 보류했던 todo 도 `done` 으로 닫는다. 방법이 바뀌었으면 `replace` 로 닫고 새 요청을 만든다.

```
<요청>
├─ ✓ Phase 1 · 파일 포맷 분석
├─ ☐ Phase 2 · 데이터 추출
│  ├─ ⏸ 보류: 원본이 암호화됨 — 설치 후 재진행     ← close([Phase 2, Phase 3], hold, …)
│  └─ ☐ 재개 · .prx 에서 추출                       ← 다음 세션이 만든 todo. 지금 작업 중
│     └─ ▹ .prx 컨테이너 해제
└─ ☐ Phase 3 · 문서 작성
   └─ ⏸ 보류: 원본이 암호화됨 — 설치 후 재진행
```

## 무엇을 쓰는가

**쓴다**: 요청 / 계획 / 결정과 그 이유 / 예상 밖의 발견 / 막힌 지점과 원인 / 방향을 바꾼 이유 /
결과와 검증 방법 / 사용자에게 남은 일.

**쓰지 않는다**: 도구 실행 하나하나 (훅이 붙인다) / 대화를 그대로 옮긴 것 / 긴 코드나 로그 전체 / 비밀값.

- 서브에이전트는 기록하지 않는다. 결과를 받으면 메인에서 요지를 쓴다.
- 기록했다는 사실을 사용자에게 매번 알리지 않는다. 시작할 때 링크만 알려주고 하던 일을 계속한다.
- 대화가 압축되거나 재개되면 훅이 root 와 지금까지 쓴 노드(id 포함)를 다시 알려준다. 그 id 로 이어 쓴다.
- 나중에 다른 세션이 이 기록을 이어받는다. 제목만 읽어도 흐름이 이어지도록 요청·결론·남은 일을 제목에 드러낸다.
